# 構造化データの方針（SEED VOCAL SCHOOL）

構造化データ＝ページの中身（誰が書いた記事か、どんな教室か等）を、検索エンジンや AI が読みやすい決まった形で書き添える物。画面には出ない。

書き方の印：【事実】出典で確かめた／【推測】確かめていないが筋の通る見立て／【未確認】確かめられなかった

## まとめ

| 種類 | 今出ているか | 推奨 | 足し方 |
|---|---|---|---|
| Article（記事） | 出ている（ExUnit） | 残す。ExUnit を 9.124.0 以上に上げて著者の小文字を直す | ExUnit の更新だけ |
| Person（著者） | 記事の著者としてだけ出ている | コーチ紹介ページに1つだけ足す | JSON-LD を貼る |
| Organization（教室） | 出ていない | 足す（EducationalOrganization） | JSON-LD を貼る（全ページ共通） |
| FAQPage（よくある質問） | 出ていない | 今は足さない。記事の中の質問と答えの文で足りる | 足すなら記事ごとに JSON-LD |

---

## 1. 確かめた事実（2026-11-15）

**FAQ の表示について、記憶より先に進んでいた。**

- 【事実】2023年8月、Google は「FAQ のリッチリザルト（検索結果に質問と答えが開く形で出る表示）は、よく知られた権威ある政府・医療のサイトだけに出す。ほかのサイトには通常出さない」と発表した。構造化データを急いで消す必要はない、とも書いている。
  出典：https://developers.google.com/search/blog/2023/08/howto-faq-changes
- 【事実】2026年5月8日の更新で FAQ リッチリザルトの説明ページに廃止の知らせが付き、2026年5月7日から Google 検索に出なくなった。2026年6月には説明ページそのものが消された。つまり今は、政府・医療のサイトにも出ない。
  出典：https://developers.google.com/search/updates （更新履歴）、https://developers.google.com/search/docs/appearance/structured-data/faqpage （消された説明ページ）
- 確かめ方の注意：この作業環境では developers.google.com を直接開けなかった（ネットワーク設定で止められている）。上の2つは、検索結果に出た公式ページの中身で確かめた。日付と文言は、公開前に人の目で上のURLを開いて確かめ直すとよい。

**記事の著者について**

- 【事実】Google は記事の著者に、人なら `Person`、団体なら `Organization` を使うよう求めている。著者を見分けるために `url`（紹介ページ）か `sameAs`（ほかのサイトのプロフィール）を使える。紹介ページがサイト内にあるなら、そのページに ProfilePage の構造化データを付けるのを勧めている。
  出典：https://developers.google.com/search/docs/appearance/structured-data/article 、https://developers.google.com/search/docs/appearance/structured-data/profile-page
- 【事実】ExUnit には、著者の種類が小文字の `person` / `organization` で出て、無効なデータとして扱われ、著者情報が検索エンジンに伝わらない不具合があった。9.124.0 で、出す時に `Person` / `Organization` に直すよう修正された（保存してある値と設定画面は変わらない）。
  出典：https://github.com/vektor-inc/vk-all-in-one-expansion-unit/issues/1495 、https://github.com/vektor-inc/vk-all-in-one-expansion-unit/pull/1526 、https://github.com/vektor-inc/vk-all-in-one-expansion-unit/releases/tag/9.124.0
- 【事実】ExUnit の著者の構造化データは、管理画面の「ユーザー > プロフィール」の「投稿者情報の構造化データ」で入れる（種類・名前・URL・sameAs）。
  出典：https://ex-unit.nagoya/ja/features/structured-data （検索結果の中身で確認。ページは直接開けなかった）
- 【未確認】ExUnit に Organization・FAQPage・Person（単独）を出す設定があるか。運営者の情報が構造化データに無いことを扱う課題（Issue #1521）が ExUnit の開発元に立っているのは見えたが、片付いたかは確かめられなかった。https://github.com/vektor-inc/vk-all-in-one-expansion-unit/issues/1521
- 【未確認】SEED のサイトの ExUnit の今の版。

## 2. 種類ごとの方針

### Article（記事）
- (a) 出ている。著者は Person／山口はるき／コーチ紹介ページ／YouTube を設定済み。ただし `"@type":"person"`（小文字）で出ている。
- (b) 残す。小文字のままだと著者が伝わっていない【事実：上の不具合】。記事の信頼感（誰が書いたか）の芯なので、いちばん先に直す。
- (c) ExUnit を 9.124.0 以上に更新するだけ。設定は変えなくてよい【事実】。更新後、Google の「リッチリザルト テスト」（https://search.google.com/test/rich-results ）で記事1本を調べ、`"@type":"Person"` になったかを見る。
- (d) 貼り込まない（ExUnit が出す）。二重に出すと食い違いの元になる【推測】。

### Person（著者・単独）
- (a) 単独では出ていない。
- (b) 足す。ただしコーチ紹介ページ1枚だけ。Google は「サイト内の著者紹介ページには ProfilePage を付ける」のを勧めている【事実】。記事の著者の `url` がこのページを指しているので、「この人は誰か」がつながる。
- (c) コーチ紹介ページだけに JSON-LD を貼る（下の「貼る場所」）。
- (d) 型（〔 〕は入れる値）:

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "ProfilePage",
  "mainEntity": {
    "@type": "Person",
    "@id": "https://seedvocalschool.com/#haruki-yamaguchi",
    "name": "山口はるき",
    "jobTitle": "ボーカルコーチ",
    "url": "〔コーチ紹介ページのURL〕",
    "image": "〔プロフィール写真のURL〕",
    "worksFor": { "@id": "https://seedvocalschool.com/#organization" },
    "sameAs": ["https://www.youtube.com/@SEEDVOCALSCHOOL"]
  }
}
</script>
```

年数・人数の実績は入れない（本人の判断）。

### Organization（教室）
- (a) 出ていない。
- (b) 足す。「どの教室の記事か」が伝わり、記事の著者（Person の `worksFor`）ともつながる。Google は `url` と `logo` で団体を見分ける【事実】。
- 種類は **EducationalOrganization を推奨**。schema.org では Organization の一種（子）なので、Organization として読む仕組みにもそのまま通じる【推測：Google の説明に一種を使ってよい旨があると記憶しているが、今回は確かめていない】。ボイトレ教室は教える場なので中身とも合う。ほかの案：Organization（いちばん無難）、LocalBusiness（店舗として住所・営業時間も出したい時。地図の検索も狙うならこちらを検討）。
- (c) 全ページ共通の head に JSON-LD を貼る（下の「貼る場所」）。トップページだけでもよい【推測】。
- (d) 型:

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "EducationalOrganization",
  "@id": "https://seedvocalschool.com/#organization",
  "name": "SEED VOCAL SCHOOL",
  "url": "https://seedvocalschool.com/",
  "logo": "〔ロゴ画像のURL。112×112px以上〕",
  "description": "〔教室の説明を1文〕",
  "sameAs": ["https://www.youtube.com/@SEEDVOCALSCHOOL"]
}
</script>
```

URL は HTTPS 化が終わってから `https://` で入れる（今の `http://` のサイトに貼るなら、HTTPS 化の作業と合わせる）。ロゴは 112×112px 以上で、検索エンジンが読める URL【事実：Organization の説明ページ】。

### FAQPage（よくある質問）
- (a) 出ていない（「検討中」）。
- (b) **今は足さない**。理由：Google の FAQ の表示は 2026年5月で終わり、説明ページも消えた【事実】。AI の回答（AI 概要など）に拾われやすくなるという公式の説明は見つからなかった【未確認】。AI が読むのは画面に出ている質問と答えの文だと考える方が筋が通る【推測】ので、記事テンプレの「よくある質問」（質問形の H3＋言い切りの答え）を守る方が効く。害は無い【事実：2023年の発表で、消す必要は無いとしている】が、記事ごとに本文と同じ文を二重に持つ手間と、直し忘れて食い違う心配がある。
- ほかの案：入れる（Bing やほかの AI が読む可能性に賭ける）。入れるなら下の型。
- (c) 入れるなら記事ごと。記事の一番下に「カスタム HTML」ブロック（Elementor の記事なら HTML ウィジェット）で貼る【推測：JSON-LD は本文の中に置いても読まれると記憶しているが、今回は確かめていない】。
- (d) 型（記事の「よくある質問」と同じ文にする）:

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "mainEntity": [
    {
      "@type": "Question",
      "name": "〔質問1〕",
      "acceptedAnswer": { "@type": "Answer", "text": "〔答え1〕" }
    },
    {
      "@type": "Question",
      "name": "〔質問2〕",
      "acceptedAnswer": { "@type": "Answer", "text": "〔答え2〕" }
    }
  ]
}
</script>
```

## 3. JSON-LD を貼る場所（Organization と Person）

| 案 | 中身 | 向き不向き |
|---|---|---|
| **A. コード挿入のプラグイン（推奨）** | WPCode など。「head に入れる」「このページだけ」を画面で選べる | テーマを更新しても消えない。外す時もボタン1つ。Organization は全ページ、Person はコーチ紹介ページだけ、と分けやすい |
| B. テーマ（Lightning）のカスタマイザーの head 挿入 | 【未確認】Lightning に head へ任意のコードを入れる欄があるか確かめられなかった | あれば手軽。ページごとに分けにくい【推測】 |
| C. ExUnit の機能 | 【未確認】head にコードを入れる設定項目があるか確かめられなかった | あれば道具が増えない |
| D. 子テーマの functions.php | PHP で head に出す | 間違えるとサイトが止まる。今回は勧めない |

推奨は A。プラグインが1つ増えるが、貼った物を一覧で見られ、戻すのも簡単なため。B か C の欄が管理画面で見つかれば、そちらでもよい（Person はページを分けられることが条件）。

## 4. 貼ったあとに確かめること

1. リッチリザルト テスト（https://search.google.com/test/rich-results ）か、schema.org の検証（https://validator.schema.org/ ）に、トップ・記事1本・コーチ紹介ページの URL を入れる。
2. エラーが無いこと、Article の著者が `Person`（大文字）になったこと、Organization と Person が読まれていることを見る。
3. Article と Person で、名前・URL が食い違っていないか（ExUnit の著者 URL＝コーチ紹介ページ）を見る。
